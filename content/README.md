# Platyko question bank

One bank of original JavaScript items serves lessons, review, the daily challenge and multiplayer.
The rules below implement sections 7, 8 and 9 of `PRODUCT_REDESIGN_PRD.md`. Types live in
`packages/content-model`; the pipeline lives in `tools/content`.

## Layout

```
content/
  units/<track>/<nn>-<unit>.json   authored: unit specification, source ledger, lessons, items
  concept-catalog.json             the four concepts of every unit and their prerequisites
  constructs.json                  language construct -> unit that teaches it (Gate D scan)
  generated/traces/<unit>.json     generated by execution, never edited by hand
  migration/legacy-triage.json     which unit converts each legacy exercise, puzzle and duel question
  migration/legacy-item-map.json   legacy key -> new item id, generated from the items' `legacyKeys`
  verification/runs/<runId>.json   one log per full pass (PRD 8.6)
  .cache/                          fetched source text for the originality check (not committed)
```

Tracks: `beginner` (8 units, 24 items each), `intermediate` (8, 24), `advanced` (7, 20),
`expert` (5, 16) — 604 items, at least 200 duel-eligible.

## Unit file

`UnitFile` in `packages/content-model/src/unit.ts`. A unit declares its concepts (with
prerequisite concept ids), its misconceptions, the sources consulted (URL, retrieval date, hash)
and four lessons. Each lesson has an ungraded concept card (a title, a body of at most 60 words,
a worked example and its exact output) and the ids of the new items it teaches, in PRIMM order:
predict, trace, fill or reorder, fix or write. Every item belongs to exactly one lesson. The app
fills a lesson to eight slots with review items, and builds the fifth, summary lesson itself.

## Item rules

`AuthoredItem` in `packages/content-model/src/item.ts`.

- **Id:** `<beg|int|adv|exp>.<unit>.<concept-slug>.<format-slug>-NN`, lower case, for example
  `int.closures.loop-var.predict-01`. Format slugs: `predict`, `trace`, `parsons`, `fill`, `fix`,
  `write`, `concept`. An id never changes once committed.
- **Code:** an array of lines, at most 12 lines of at most 36 characters, two-space indentation,
  no tabs, no trailing spaces. `PARSONS` has at most 8 lines.
- **Options:** exactly three; exactly one correct. Every option carries its own `feedback`. A wrong
  option names the `misconception` it encodes (an id declared in the unit file).
- **Hints:** three, in rising strength: a pointer ("Look at line 3"), the concept, a near-solution.
  A hint never states the answer.
- **Reference:** one MDN or ECMA-262 page where the learner can read more. A pointer, not a source.
- **Duel-eligible** formats: `PREDICT_OUTPUT`, `PARSONS`, `FILL_BLANK`, `FIX_BUG`, `CONCEPT_MCQ`,
  with `timeLimitSec` between 15 and 45.
- **Prose:** plain, direct English. No jokes that need cultural context, no trick wording.

### Per format

| Format | Authored fields | Meaning |
|---|---|---|
| `PREDICT_OUTPUT` | `code`, `options`, `solution.expectedOutput` | Each option text is a complete candidate output. |
| `TRACE` | `code`, `options`, `solution.probe`, `solution.expectedOutput` | The learner picks the value of `probe.variable` right after `probe.afterLine` has run for the `probe.visit`-th time. Options are values in canonical form (a string in single quotes); `expectedOutput` is what the snippet prints. |
| `PARSONS` | `code` (shuffled), `solution.lineOrder`, `solution.acceptedOrders`, `solution.expectedOutput` | `lineOrder` lists indices into `code` forming the correct program. No distractor lines. |
| `PARSONS` + `variant: "ORDER_OUTPUT"` | `code`, `solution.expectedOutput` | The learner orders the printed lines. At least three lines, all different. |
| `FILL_BLANK` | `code` with `___`, `options` (chips), `solution.blanks`, `solution.expectedOutput` | `blanks[i]` lists the chips accepted in blank `i`. A chip is `correct` when some blank accepts it. One to three blanks, three to six chips. |
| `FIX_BUG` | `code` (buggy), `options` (replacement lines), `solution.bugLine`, `solution.expectedOutput` | The learner taps the buggy line, then picks the replacement. `expectedOutput` is the fixed program's output. |
| `CODE_WRITE` | `solution.entry`, `solution.tests`, `solution.reference`, `solution.wrongSolutions` | An expression over named variables, or a function body. At least three tests and three wrong solutions. `code` is optional context. |
| `CONCEPT_MCQ` | `code`, `options`, `solution.expectedOutput` | The snippet demonstrates the claim made by the correct option; its output is `expectedOutput`. |

### Lesson recipes

`content/concept-catalog.json` fixes the four concepts of every unit, one per lesson, with their
prerequisites; a unit file declares exactly those concepts. Each lesson teaches its concept with
this many new items, in this order (PRD 6.4):

| Track | New items per lesson | Recipe |
|---|---|---|
| Beginner | 6 | `PREDICT_OUTPUT`, `PREDICT_OUTPUT`, `TRACE`, `FILL_BLANK`, `PARSONS`, then `CONCEPT_MCQ` in lessons 1 and 3 and `CODE_WRITE` (an expression) in lessons 2 and 4 |
| Intermediate | 6 | `PREDICT_OUTPUT`, `CONCEPT_MCQ`, `TRACE`, `FILL_BLANK` or `PARSONS` (alternate), `FIX_BUG`, `CODE_WRITE` |
| Advanced | 5 | `PREDICT_OUTPUT`, `CONCEPT_MCQ`, `FILL_BLANK` or `PARSONS`, `FIX_BUG`, `CODE_WRITE` |
| Expert | 4 | `PREDICT_OUTPUT`, `CONCEPT_MCQ`, `FIX_BUG`, `CODE_WRITE` or `FILL_BLANK` (alternate) |

Units about asynchronous order (`async-basics`, `promises-in-depth`, `event-loop`) use the
`ORDER_OUTPUT` variant for their `PARSONS` slots. The `dom-and-events` unit has no `CODE_WRITE`
(the sandbox has no DOM): those slots are `PARSONS` or `FILL_BLANK` against the drawn tree. The
`modules` unit cannot execute `import` or `export`: its snippets show the same behaviour with
module-pattern code, and the syntax appears only in prose.

Difficulty rises inside a lesson and across a unit: 1 to 2 in Beginner, 2 to 3 in Intermediate,
3 to 4 in Advanced, 4 to 5 in Expert.

### Practical notes for authors

- **Legacy items** keep their concept, not their suggested format: when a lesson has no free slot
  of the suggested format, convert the item into whichever recipe slot is free.
- **Parsons orderings.** Gate A runs every ordering, so lines that print the same thing, or
  independent declarations, create extra valid orders. Give each printed line a distinct value
  and make each line depend on the one before it; otherwise record the extra orders.
- **Function declarations are hoisted**, so a one-line declaration may sit anywhere in a Parsons
  program; prefer `const name = (…) => …` or programs where order is forced by data.
- **TRACE probes** may sit on a line that calls a function: a call returning to the line is not a
  new visit.
- **TRACE probes read a variable by name.** Give the probed variable a name that no inner
  scope shadows.
- **MDN links.** Glossary pages live under `https://developer.mozilla.org/en-US/docs/Glossary/`,
  not under `/Web/JavaScript/`. Not every term has a page (there is no `Glossary/Currying`); the
  online verify run reports broken links.
- **TRACE probes cannot read a `catch` parameter**; probe a variable of the enclosing scope.
- **Caught values are printed through an expression** (`'got ' + reason`): the banned-construct
  scan flags `console.log(caught)` whatever the caught value is, because it cannot know it is not
  an Error.
- **`instanceof` belongs to the prototypes unit**; earlier units observe errors and promises
  through `.name`, custom properties or `typeof`.
- **CODE_WRITE runs synchronously** and its tests compare returned plain data: no timers, no
  awaited promises, and no "this call throws" assertion. Promise, async and error concepts test
  the synchronous core (a `then` handler's body, the logic after an `await`, `try`/`catch`).
- **The 36-character line limit** applies to every code line an item shows, including FIX_BUG
  replacement lines and CODE_WRITE solutions, indentation included.
- **Prompts are compared across all units** for near-duplicates: write a prompt specific to the
  snippet rather than a stock one ("The program should print 2. Tap the buggy line…").

### Writing feedback, hints and explanations

- The explanation says why the right answer is right, in at most 60 words, and names the rule.
- A wrong option's feedback addresses the thought that leads to it ("You added 1 + 2 + 3. The
  loop starts at 0, so it adds 0 + 1 + 2.") and never just says "wrong". It does not reveal the
  correct answer: the learner gets a second attempt.
- Hint 1 points at a place ("Look at line 3"). Hint 2 states the concept. Hint 3 narrows the
  choice without naming the answer.
- Address the learner as "you". No exclamation marks, no praise words, no filler.

## Execution model

Items run in the pipeline's own runner so that a stated answer is a fact, not an opinion.

- **Globals:** the ECMAScript built-ins, `console.log`, `setTimeout`, `clearTimeout`,
  `setInterval`, `clearInterval`, `queueMicrotask`, and `document` when the item declares `dom`.
- **Timers** are a virtual queue ordered by delay, then by insertion. Microtasks are the engine's.
- **Canonical output.** `console.log` joins its arguments with one space. A top-level string
  prints raw. Inside a container a string prints in single quotes. Numbers, booleans, `null`,
  `undefined`, bigint (`10n`) and symbols (`Symbol(tag)`) print as written; `-0` prints `-0`.
  Arrays: `[1, 2, 3]`, holes as `empty`. Plain objects: `{a: 1, b: 'x'}`, keys quoted only when
  not identifiers. Class instances: `Point {x: 1}`. `Map(2) {'a' => 1, 'b' => 2}`.
  `Set(2) {1, 2}`. Functions: `[Function: name]` or `[Function (anonymous)]`; classes:
  `[class Name]`. Nesting deeper than three levels is a pre-check finding.
- **Uncaught error:** prints the line `Uncaught <ErrorName>`, for example `Uncaught TypeError`;
  a thrown non-error value prints `Uncaught <value>`. An unhandled promise rejection prints
  `Uncaught (in promise) <ErrorName>` once the microtask queue has drained. Message text is never
  part of an answer. As in a browser, an uncaught error ends only the task that threw: timers and
  microtasks already queued still run.

### Banned in snippets (PRD 7.3)

`Math.random`, `Date`, `Intl`, `toLocale*`, `localeCompare`, the text of error messages
(`.message`, `.stack`, printing an error object), `process`, `require`, `import`, `globalThis`
tricks, `eval`, `new Function`, `with`, labels, and timers whose delays are different but less
than 100 ms apart. `var` is allowed only where the item teaches it.

## Originality (PRD 9)

- Write from the unit specification: the concept and the misconception. Never from an existing
  question, and never from a source's wording.
- Invent every snippet: your own identifiers, values and program shape. No snippet is taken from
  any source, including permissively licensed ones.
- Record every page consulted in the unit's `sources`. Sources inform topic coverage and ordering
  only.
- The pipeline compares prose and normalised code against the ledger sources and against the
  whole bank. A `FAIL` blocks the item.

## Verification (PRD 8)

| Step | Nature | Command |
|---|---|---|
| Pre-check | Mechanical: schema, limits, banned constructs, duplicates, reference links, originality | `npm run content:verify -- --precheck-only` |
| Gate A | Mechanical: every snippet executed; traces generated | `npm run content:verify` |
| Gate B | Blind solver agent; mechanical comparison with Gate A | verification loop |
| Gate C | Independent clarity review | verification loop |
| Gate D | Independent difficulty and track-fit review, plus the construct scan | verification loop |

A full pass runs every step over the entire bank. Any finding sends the item back; after a fix,
every gate runs again over the entire bank. The loop ends on the third consecutive clean pass over
an unchanged bank. The seed marks items `LIVE` only when the bank hash equals the hash recorded by
that run.
